## Como trabalhamos

### Como as tarefas chegam

- Nos projetos recentes, o enunciado do professor e as necessidades identificadas para o StartUP orientaram o trabalho.
- No Projeto 3, a equipe separou a entrega em métricas de produto, métricas de código, painel e documentação.
- Essa divisão permitiu que as partes avançassem em paralelo; a prioridade do produto foi discutida coletivamente.
- Neste Projeto 4, vamos registrar novas tarefas como issues, com objetivo, responsável e critério de conclusão.

### Como decidimos quem faz o quê

- No Projeto 3, as responsabilidades foram distribuídas para permitir trabalho em paralelo.
- O registro descreve as funções da equipe, mas não informa como os responsáveis foram escolhidos em cada tarefa.
- As prioridades do produto ficaram a cargo da equipe, em vez de uma decisão individual.
- Para este projeto, vamos combinar o responsável em grupo e registrar a decisão na issue; a divisão pode ser revista se alguém ficar bloqueado ou sobrecarregado.

### Definição de Pronto

Uma tarefa estará pronta quando:

- [ ] o resultado atende ao objetivo e aos critérios registrados na tarefa;
- [ ] o código, protótipo, cálculo ou documento foi conferido de acordo com o tipo de entrega;
- [ ] os testes ou verificações aplicáveis passaram, ou a limitação foi registrada;
- [ ] a documentação relacionada foi atualizada;
- [ ] pelo menos outra pessoa da equipe revisou o resultado;
- [ ] a issue foi atualizada com o resultado e evidências, e está pronta para ser fechada.

### O que fazemos quando alguém trava

- Os registros anteriores não especificam um procedimento para bloqueios; neste projeto, vamos usar o fluxo abaixo.
- Avisar no grupo do WhatsApp, explicando o objetivo, o ponto do bloqueio e as tentativas feitas.
- Usar o modelo de pedido de ajuda abaixo para que outra pessoa consiga reproduzir o problema.
- Se o bloqueio durar um dia letivo ou ameaçar um prazo, combinar uma conversa rápida e pedir apoio ao professor, se necessário.

## Combinados de comunicação

> O Projeto 3 registra o uso de uma issue do GitHub para acompanhar a ação prioritária, mas não documenta os canais nem os tempos de resposta habituais. Para o Projeto 4, adotamos os seguintes combinados:

| Combinado | Acordo da equipe para este ciclo |
|---|---|
| Tempo de resposta esperado | Até um dia letivo; não é necessário responder imediatamente. |
| Horário em que ninguém precisa responder | Das 20h às 7h, fins de semana e feriados. |
| Qual canal para cada assunto | Grupo do WhatsApp para alinhamentos rápidos e bloqueios; GitHub Issues para tarefas, decisões e acompanhamento; pull requests para revisão de código. |
| O que conta como urgente | Bloqueio que impede outra pessoa de trabalhar ou risco de perder um prazo nas próximas 24 horas. Avisar no grupo e mencionar a pessoa responsável. |

### Modelo de pedido de ajuda

```text
1. O que eu quero fazer
2. O que está acontecendo
3. Onde (arquivo, tela, rota)
4. O que eu já tentei
5. O que eu preciso de você
```

### Modelo de daily por texto preenchido pela equipe

```text
ONTEM: Revisamos os dados e a decisão do Projeto 3 para retomar a prioridade de melhorar o cadastro e o primeiro acesso.
HOJE: Finalizamos o manual de operação, organizamos o backlog com MoSCoW e RICE e revisamos os PDIs.
TRAVADO: Não há bloqueio técnico. As pontuações RICE são estimativas e deverão ser recalculadas quando houver dados reais de uso e esforço.
```
